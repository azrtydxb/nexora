Review found that a healthy new partner does not protect a legacy VIP selector that still excludes it. The sequencing core therefore requires non-restarting label enrolment of the existing pods, verification of all labelled endpoints, and pair-selector cutover **before** the first rolling replacement. The runtime adapter must use UID/resourceVersion preconditions, reject unknown endpoint identities, and support diagnosis/resumption of partial enrolment/cutover. The enrolment/rollout adapters, live probe configuration and script integration remain unimplemented. Failures retain the lock by design; no automatic expiry or takeover is permitted while an old remote Helm operation may still finish.

Lock-adapter progress: `deploy/kwrollout/lock.go` implements a non-expiring release-scoped ConfigMap lock via bounded, explicit-context `kubectl` operations. Unique create or JSON Patch compare-and-swap claims an empty lock; UID/resourceVersion/protocol/owner tests protect updates and release. Release clears ownership rather than deleting the object. Every acquisition gets a fresh owner token. The sequencing core checks ownership again before each apply and label enrolment. Review identified missing pre-mutation ownership checks and reusable-owner-token risk; regression tests now cover both, along with contention, ambiguous create responses, cancellation, malformed lock objects and stale-release races.

## 2. Safe migration and deployment orchestration

Files: `scripts/kw-deploy.sh`, new focused rollout helper and executable tests under the existing Go workspace, `scripts/kw-acceptance.sh`.

- Acquire a cluster-scoped-to-this-release deployment lock with ownership-safe release; block competing invocations before mutations.
- Inspect live pods, controllers, Services and EndpointSlices. Detect old two-engine versus new four-engine topology; reject unknown/inconsistent states.
- During initial migration, keep existing VIP selectors until the new partners and pair-labelled existing pods are verified. Enrol existing pods without replacement using UID/resourceVersion-preconditioned label patches; verify actual pair endpoints and switch selectors before rolling any existing member. Do not overwrite existing node state or synthesize extra policy groups.
- Roll one instance at a time, retaining surge/drain readiness. Require partner health before starting and require the expected image/configuration, management connection and direct DNS answers before proceeding.
- Verify both client VIPs continuously. Halt on observed loss or failed health checks; do not advance to a partner. Default raw Helm upgrades remain frozen until the guarded workflow resumes.
- Finish with all instances frozen and both Services selecting their verified pairs. Update dynamic engine discovery rather than hardcoding only a/b.
- Exercise ordering, failed partner, stale configuration, failed DNS, lock contention and interrupted/resumed migration with runnable tests and mocked command/API boundaries. No production exercise until these pass.
