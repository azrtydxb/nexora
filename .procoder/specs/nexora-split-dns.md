# Nexora split-horizon DNS

Status: draft — planning scope approved: include unsigned/signed primary and secondary views in the first release. Detailed design remains subject to review; no implementation or production change is authorized by this document.

## Problem

The same hosted name must return private addresses to internal clients and public addresses to other clients. Current zone query ACLs allow or deny a query; they do not select different records. `zones.name` is globally unique, `AuthSet` rejects duplicate origins, and `AuthZone` snapshots and UPDATE/NOTIFY messages principally identify zones by name. Allowing duplicate origins alone would therefore be unsafe.

## Users

- Operators managing internal, VPN and external clients of the same application.
- GUI/API users who need to inspect which records a client will receive.
- Maintainers responsible for preserving authoritative DNS, access control and rolling-upgrade safety.

## Example

Zone `example.com.` has two complete views:

| View     | Source networks                          | app.example.com. A |
| -------- | ---------------------------------------- | ------------------ |
| default  | Clients not matching a named view        | 203.0.113.50       |
| internal | 192.168.10.0/24, 10.20.0.0/16, fd20::/48 | 192.168.10.50      |

Addresses are illustrative; 203.0.113.0/24 is documentation space. The default view is not automatically public: listening interfaces, firewalls, delegation and query ACLs still control reachability.

## In scope

- [S-1] **Zone families and complete views.** One logical origin has exactly one default view and zero or more named views. Existing zone IDs, records and behavior become the default without an operator action. A named view has its own records, SOA, TTLs, serial, image and journal. It never inherits missing records from another view. Offer an explicit one-time clone of default records when creating a view; subsequent changes are independent.
- [S-2] **Selection.** First find the longest hosted zone suffix using existing authoritative and DS-at-child-apex semantics. Within that family, select the matching named view with the longest client prefix; otherwise use default. IPv4 and IPv6 are supported. Canonicalize prefixes and IPv4-mapped IPv6 client addresses. Reject a canonical prefix assigned to two named views of one family; overlapping unequal prefixes are permitted. Reject mapped-IPv6 CIDRs with a clear instruction to use IPv4 notation. Named views require at least one prefix; default has none. No hidden RFC1918, loopback or link-local classification.
- [S-3] **Source identity and authorization.** Use the engine's transport peer address for UDP, TCP, DoT, DoH and DoQ. Do not select from arbitrary HTTP headers or EDNS Client Subnet. Document that a recursive resolver, NAT or proxy can hide the original client. Select the view before checking its query ACL. A denied selected view returns REFUSED, never another view or recursion. Recursion permission remains independently enforced; serving the default view must not turn Nexora into an open resolver. Views are separate from filter policy groups and share the family's engine-group placement.
- [S-4] **Answer isolation.** All record types use the selected view, including AAAA, CNAME, MX, SRV, TXT, HTTPS/SVCB, NS and PTR. Wildcards, referrals, additional records, SOA, NXDOMAIN and NODATA derive only from that view. A missing name remains NXDOMAIN even if present in default. A failed/expired selected view fails closed with SERVFAIL, never default or recursive fallback. CNAME processing that continues into another hosted family reselects using the same source identity. Preserve existing DS parent-side lookup while selecting the parent's view independently.
- [S-5] **Cache and runtime isolation.** View selection precedes any reusable authoritative answer lookup. Cache keys, in-flight coalescing, negative caching, stale serving, refresh work and persisted runtime indexes that can hold view-dependent answers must include stable concrete view identity and relevant configuration generation, or explicitly bypass those caches. This applies to the default view too. A matcher edit invalidates affected selection state. Atomic snapshot replacement never exposes half of a family. An invalid snapshot leaves the previous complete runtime serving.
- [S-6] **GUI and API.** Add a Views section to zone details, with default clearly distinguished, CIDRs, clone/create/edit/delete and a source-IP preview. Keep the selected view visible in records, import/export and transfer settings. Preview reports the selected view and query ACL result; it does not simulate the full DNS resolution/filter chain. API mutations retain existing roles, optimistic revisions and audit behavior. Show default-view exposure and shared-resolver limitations before enabling a split zone. Never automatically copy private answers to default.
- [S-7] **Observability.** Authoritative query logs and traces record logical zone ID and concrete view ID/name, including denials and negative answers. All configured query-log backends preserve and filter these fields; old records decode with absent attribution. Audit logs identify the concrete view and matcher edits. Do not use client IPs as Prometheus labels. A bounded view-selection failure counter is sufficient for the first release.
- [S-8] **Transfer isolation.** AXFR/IXFR normally select by the transfer connection's source, then enforce the selected view's transfer ACL and TSIG authorization. To replicate multiple views from the same secondary address, support an explicit authenticated transfer binding from TSIG key identity to concrete view within a family; a successfully verified bound key selects only that view, still subject to its source ACL. This exception applies only to AXFR/IXFR and authenticated SOA queries at the family apex using an explicitly bound transfer key; apply transfer ACLs to those SOA queries too. It never changes selection for other client answers or UPDATE. Reject ambiguous bindings, invalid/unknown keys and failed ACLs without trying another view or dropping to unsigned access. Each view owns its serial and journal; equal serial numbers in different views cannot share deltas. Split-family transfers require explicit peer CIDRs and TSIG. NOTIFY targets and TSIG bindings belong to the concrete view. The same secondary address can receive notifications for multiple views with distinct keys. Unchanged single-view transfers continue to work.
- [S-9] **Dynamic UPDATE isolation.** Select the target view from the UPDATE source and authorize with its existing TSIG/source policy. Forward immutable zone/view IDs plus observed source to management; management verifies family membership, active selection and permissions again. A matcher change during forwarding refuses the stale request rather than updating another view. Prerequisites, journal changes and serial increments affect only that view. UPDATE targeting a secondary is refused without rerouting to a primary sibling. Existing non-view UPDATE clients remain compatible.
- [S-10] **DNSSEC for all views.** Signed primary views are supported in the first release, with independently owned KSK/ZSK material, DNSKEY/RRSIG records, NSEC/NSEC3 chains, signing policy, signature refresh and rollover state. No automatic private-key sharing, signature reuse or denial-chain union across views. DNSKEY and denial answers follow the selected view. Sign UPDATE and imported records within that view's transaction/publication lifecycle. A clone of signed records regenerates signing artifacts with fresh keys if signing is requested; it never copies DNSKEY/RRSIG/NSEC/NSEC3 as editable user records. DS export, rollover acknowledgments and signing APIs/UI target a concrete view. Existing signed zones keep their IDs and key material as default. Parent DS consistency and signed-secondary handling are specified below; neither is deferred.
- [S-11] **Safe activation and upgrades.** View-capable engines advertise a protocol capability. Management refuses activation while any non-deleted/non-revoked engine assigned to the family lacks that capability, including disconnected engines whose capability is unknown. Snapshot delivery independently refuses to send a split-view configuration to an incompatible engine. Old engines must never receive private records as an accidental default. Upgrade software with single-view configuration first, activate views only after compatibility checks. Keep the new binary when rolling configuration back to default-only; binary downgrade with active views is unsupported and must be blocked by deployment preflight.
- [S-12] **Bounds.** Proposed limits: 32 views per family including default, 128 CIDRs per named view, label 1–63 lowercase alphanumeric/hyphen characters; `default` reserved. Existing per-record/input bounds remain. Snapshot memory budgets account for every image, journal and matcher; over-budget builds reject atomically. Matching is local, allocation-free on the normal query path, with no management/database call per query.

- [S-13] **Secondary views.** A concrete view may be primary or secondary independently of its siblings, including mixed families and signed secondary views. Each secondary owns its primary endpoints, outgoing source binding, TSIG credentials, SOA timers, refresh/retry state, serial, image, journal and expiry. Bootstrap SOA, AXFR, IXFR, periodic refresh, NOTIFY-triggered refresh and failover use the same explicit per-view upstream binding. An upstream endpoint/key/source tuple must unambiguously select the intended upstream view; reject duplicate tuples assigned to different local views of one family. Configure source binding for source-selected upstreams or view-specific TSIG for upstreams supporting key selection, including Nexora's S-8 binding. Never invent a nonstandard DNS view field. Primary failover stays within the concrete view's configured replica set. Incoming NOTIFY is authenticated and routed by family, primary peer and view-specific TSIG binding, not the client's query CIDRs or an origin-only lookup. Reject ambiguous or unbound notifications; never refresh every sibling as a guess. Views may serve signed transfers without local private keys or resigning. Record editing and local signing remain primary-only operations. Kind conversion is explicit and atomic for one view, never an implicit conversion of siblings.

## DNSSEC trust and secondary lifecycle

- Proposed key model: independently managed keys per primary view; no family-wide shared-key controller. Keys, signature caches, salt/denial parameters, maintenance jobs, rollover locks and DS acknowledgments are indexed by concrete ID. Concurrent rollovers with colliding key tags or serials cannot cross views. Key tags alone are not identity.
- A validating resolver must see a consistent chain for the view it uses. A common signed parent may publish a DS RRset containing the KSK digests of all signed child views; alternatively split parent views publish the DS for the corresponding child view. Neither model publishes private record contents. Nexora supplies per-view DS exports and a family summary, but does not mutate an external parent automatically. Rollovers retain each view's old key through the applicable DS/DNSKEY TTL and acknowledgment window independently.
- Hosted-parent checks evaluate parent and child selection across relevant CIDR intersections, not by matching view labels. Activation and rollover diagnostics report missing/mismatched DS and parent-view exposure. External parent readiness requires recorded operator acknowledgment and validation from the intended resolver networks; absence of visibility is reported as unknown, never successful validation. An unsigned child view below a visible secure delegation is bogus; require an explicitly insecure parent delegation in that resolver context rather than disabling validation silently. Mixed signed/unsigned families are supported only with a consistent per-context delegation or explicit local trust policy.
- DNSSEC acceptance must use actual validating resolvers with suitable test trust anchors. Ordinary authoritative answers do not gain AD merely because Nexora signed them. For forwarding resolvers, changing the client-facing view without isolating that resolver's cache/validation context is not safe: DNSKEY, DS, aggressive negative caching and ordinary records all require consistent resolver context. Document this along with NAT limitations.
- A signed secondary retains the transferred DNSKEY/RRSIG and denial records, preserves their wire semantics and never generates replacement signatures locally. Its transfer binding authenticates the upstream view; TSIG is not DNSSEC validation. When a transfer-validation DS/trust-anchor policy is configured, validate the candidate against that concrete policy before publication and reject bogus data. Even without optional local validation, end-to-end validation of served signed transfers is mandatory release evidence.
- Conversion from signed secondary to locally signed primary requires fresh local keys and explicit DS/trust readiness before atomic activation; do not treat upstream signatures as locally maintained signing state. Conversion to secondary stages a successful transfer before retiring the local signer, and concurrent signer/transfer jobs cannot overwrite the new kind. Failure preserves the prior active configuration and image.
- Refresh/transfer jobs pin concrete view ID and configuration generation. A rebind, conversion or deletion while a job is in flight rejects stale completion; never writes a fetched image into another view. Failed IXFR falls back to AXFR only on that same view binding. Malformed/incomplete transfers keep the last good image until its own SOA expiry; that expired view returns SERVFAIL while healthy siblings continue serving. SERVFAIL also applies when required DNSSEC signatures are no longer valid for a signed response; never strip signatures to make an expired signed view appear unsigned. Refresh and signature-expiry failures are attributed separately.
- Incoming NOTIFY forwarding carries observed peer, verified TSIG identity, concrete view ID and binding revision over the authenticated control channel. Management rechecks membership and binding before scheduling. A wire NOTIFY does not carry a trusted view ID. Unauthenticated/ambiguous split-family NOTIFY cannot choose or wake a view. Existing single-view NOTIFY semantics remain compatible.

## Out of scope

- GeoIP, ECS-based selection, arbitrary HTTP-header trust, user-identity selection and automatic NAT discovery.
- Recursive/forward-zone upstream selection, weighted routing, health-based answers and record-overlay inheritance.
- Automatic public DNS delegation, firewall changes or exposing management/recursion to the Internet.
- Automatic external-parent DS publication and automatic upstream-view discovery. DNSSEC signing, signed/unsigned secondary ingestion and their complete isolation are in scope, not follow-up milestones.

## Constraints

- Preserve the existing single-view API and wire behavior, authoritative ACLs, filtering precedence and DNSSEC tests.
- Client-IP selection is routing policy, not cryptographic authentication; transfers and updates still require their authorization checks.
- The database and snapshot enforce invariants independently of GUI validation.
- Test/build in the Linux dev pod. No milestone closure based on skipped or weakened assertions.
- Do not renumber proto fields. Register a new feature range after checking all reserved allocations; generated code comes from the existing generation commands.

## Interfaces

Proposed API under `/api/v1`:

- `GET /zones/{default_id}/views`: enumerate default and named views.
- `POST /zones/{default_id}/views`: create named view with label, CIDRs and explicit `clone_default` choice.
- `PATCH /zones/{default_id}/views/{view_id}` and `DELETE ...`: revision-checked matcher/label changes and named-view removal.
- `POST /zones/{default_id}/views/preview`: read-only evaluation of an operator-supplied IP, with view identity and query ACL result; no outbound DNS request.
- Existing `/zones/{concrete_id}/records`, import/export, DNSSEC lifecycle/DS export and secondary refresh/settings endpoints operate on that concrete view. Add per-view upstream source/key bindings, authenticated transfer bindings, signing/transfer validation status and a family DS summary. Kind is explicit at view creation; secondary creation requires upstream bindings and a successful bootstrap before activation. `/zones` continues listing logical/default zones, with view counts; responses expose parent/default ID for named views.
- Root deletion with named views returns conflict unless an explicit audited cascade operation is requested. Named-view deletion warns that its clients will use the next matching view/default. Default cannot be deleted separately or renamed as a view.
- Protocol adds stable family/view IDs and match prefixes to `AuthZone`, a capability to engine Hello, and concrete view identity to UPDATE/NOTIFY events where needed. Legacy messages without IDs are accepted only for single-view families. Matcher validation and capability gating occur before publication.

## Data

Proposed migration preserves `zones.id` as the concrete storage identity, reusing record/image/journal foreign keys. Add nullable `view_of` referencing the default zone, `view_name` and `match_client_cidrs`; existing rows remain defaults. Replace global name uniqueness with a partial unique origin index for defaults and a unique `(view_of, view_name)` index for named views. Enforce same origin, concrete kind/signing/replication consistency, shared engine-group placement, no nested views and matcher conflict rules in transactional service validation, with constraints/triggers for invariants expressible at the database level. Concurrent view mutations lock the default row; deleting/renaming/moving a family updates it atomically.

Record edits continue to bump the concrete primary view serial; secondary serials come from that view's upstream. Matcher-only edits bump configuration revision, not DNS serial. Clone is an explicit primary-record operation producing new record IDs without copying signing artifacts/keys, journals, transfer credentials or UPDATE grants. A secondary is bootstrapped from its own upstream, not cloned as a populated replica. New views remain staged until their matcher, keys/trust readiness (if signed) and initial image are ready; activation is atomic. Persist upstream and transfer/NOTIFY bindings with concrete view IDs, role, peer/source, secret references and revision; enforce binding uniqueness within each family. Root settings cannot bypass isolation via legacy endpoints. Old API clients retain default-only semantics. Downgrade migration refuses while named views exist rather than deleting them.

## Edge cases and failure modes

- Equal normalized prefixes conflict; prefix overlap selects most-specific. IPv4 and IPv6 defaults are explicit and independent.
- Most-specific child zone with no matching named view uses its own default, not the parent's view. An unavailable child does not leak parent or recursive answers.
- Invalid or unavailable transport source fails closed when a split family is involved; never treats an unparseable source as default. A valid source matching no named view uses default.
- ACL denial, NXDOMAIN, NODATA, CNAME loops, wildcards and glue must not cause a view fallback.
- An expired secondary or signing failure affects only the selected view. A fresh sibling with the same serial cannot supply its image, denial proof or refresh state.
- A disconnected engine cannot cause validation to assume support. New enrollment into a split-enabled group must prove capability before receiving configuration.
- A failed persistence/build/publication operation leaves the previous family and matcher usable. A successful change is acknowledged only through existing fleet rollout semantics.
- Snapshot restart and incremental image/delta replay identify views by ID, never only origin or serial. Cross-view blob/delta substitution is rejected.
